# Phase 1 Product Requirements Document (PRD)

This document establishes the product requirements for **Phase 1 (Upstream Demand & Procurement Planning)** of the Green Leaf ERP redesign. 

The goal is to implement the daily demand collection system from retail shops, enforce cutoff validation, allow managers to approve/reject demands, and compile them into a consolidated procurement view for suppliers.

---

## 🎯 Scope Boundaries

### In Scope
1. **Shop Ordering**: Requisition creation and daily demand submission by Shop Owners.
2. **Deadline Engine**: Cut-off validation at 9:30 PM, status tagging, and routing of late submissions.
3. **Purchase Approval**: Purchase Manager approval workspace, late order overrides, and comments tracking.
4. **Consolidated Procurement Table**: Aggregate approved order items grouped by product SKU.

### Out of Scope (Deferred to Later Phases)
* Warehouse receiving, inspection, and discrepancy handling.
* Sorting, grading, and batch allocation.
* Picking list generation, route loading, dispatch, and delivery.
* Financial ledger entries and invoicing.

---

## ⚙️ Functional Requirements

### 1. Shop Ordering Module

#### Overview
Shop Owners require a simple, fast interface to log their shop's inventory requirements for the next day.

#### Detailed Specifications
- **Draft Creation**: Shop Owners can add products to a daily draft order, specify quantities, edit lines, and delete items.
- **Single Active Draft Constraint**: A shop can have at most one active `Draft` order per business date.
- **Immutable Snapshot on Submission**: Once the Shop Owner clicks "Submit", the order is locked. The quantities are frozen, and the status changes to `Submitted`. The owner can no longer edit the order unless a Purchase Manager explicitly rejects it or unlocks it.
- **Automatic Metadata Capture**: Every submission must automatically record the shop identity, the user ID of the submitting Shop Owner, and the exact timestamp.

---

### 2. Deadline Engine

#### Overview
Standard operations depend on ordering by a set cutoff time (9:30 PM) so that consolidation and buying can occur overnight.

#### Detailed Specifications
- **Deadline Configuration**: The cut-off time is set to `21:30:00` (9:30 PM) in the system's timezone (`Asia/Kuala_Lumpur`).
- **Automated Evaluation**: When an order is submitted:
  - If the submission time is $\le$ 9:30 PM, it is tagged as `submission_type = on_time` and routed to the default approval queue (`state = Submitted`).
  - If the submission time is $>$ 9:30 PM, it is tagged as `submission_type = late` and routed to the late order queue (`state = LateSubmission`).
- **Deadline Override Policy**: Admins can configure temporary deadline extensions (e.g., during holidays or supply chain disruptions).

---

### 3. Purchase Approval Module

#### Overview
A centralized workspace for Purchase Managers to review shop demands and determine what will be procured.

#### Detailed Specifications
- **Manager Dashboard Queue**: Shows two lists of orders:
  - Standard submissions (Approved/Rejected in bulk or individually).
  - Late submissions (Require explicit override reasons).
- **Fulfillment Quantity Calibration**: Purchase Managers can adjust the approved quantity of individual order items down if they know supply is short, logging the reason in the item comments.
- **Decision Pathways**:
  - **Approve**: Transitions order state to `Approved` (or `ManagerOverrideApproved` for late orders).
  - **Reject**: Transitions order state to `Rejected`. Requires a mandatory comment.
- **Append-only History**: All decisions must write a record to the `approvals` audit table including the decider's user ID, timestamp, decision, and comments.

---

### 4. Consolidated Procurement Table

#### Overview
An automated engine that sums all approved shop demands by product SKU to prepare a clean shopping list for supplier procurement.

#### Detailed Specifications
- **Exclusion Rules**: Meticulously exclude all orders in `Draft`, `Submitted` (awaiting approval), `LateSubmission`, `Rejected`, or `Cancelled` states.
- **SKU Aggregation Logic**:
  - Group all approved order items by `product_id`.
  - Calculate `total_required_qty = SUM(approved_qty)`.
  - Display the UOM (unit of measurement) from the product master.
- **Consolidation Lock**: Once generated by the Purchase Manager, the procurement batch is locked, creating a snapshot table mapping back to the source shop orders.

---

## 🔒 Non-Functional Requirements

### 1. Security & Role-Based Access Control
* **Shop Owner**: Can only create, view, and submit orders for their assigned shop.
* **Purchase Manager**: Full access to review, adjust, and approve all shop orders, and generate the consolidated procurement table.
* **Admin**: Governance override capabilities, timezone configs, and audit log access.
* **Viewer**: Read-only access to dashboards.

### 2. Audit Trail & Compliance
* All state transitions must be captured in the Spatie activity log.
* Changes to shop orders and approvals must trigger Owen-It audits.

### 3. Performance
* Consolidated table aggregation must execute in $\le 500\text{ms}$ for up to 50 active shops and 200 product lines.
